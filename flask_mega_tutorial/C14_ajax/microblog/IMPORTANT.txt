Чтобы в дальнейшем, при разростании приложения, можно было дополнять/изменять таблицу новыми столбцами, нужно создать
репозиторий миграции (migrations). Для создания репозитория миграций для данного приложения, необходимо, находясь в директории microblog,
ввести в консоли две команды:
    1 - export FLASK_APP=microblog.py  - установка переменной среды. Указывает интерпретатору с каким приложением работать
    2 - flask db init  - создает каталог migrations с несколькими файлами и подкаталогом versions внутри.
Есть два способа создать миграцию базы данных (перенос данных из модели в таблицу БД): вручную или автоматически. Чтобы
сгенерировать миграцию автоматически, Alembic сравнивает схему базы данных, определенную моделями баз данных, с фактической
схемой базы данных, используемой в данный момент в базе данных. Затем скрипт миграции заполняется изменениями, необходимыми
для приведения схемы базы данных в соответствие с моделями приложений. Для автоматической генерирования миграции необходимо
ввести в консоль команду:
    flask db migrate -m "users table" # -m "users table" - это комментарий к миграции и он необязателен
Все выполненные миграции записываются в соответствующий файл в директории: migrations/versions. После выполнения миграции
последняя строка в консоли сообщает где записана выполненная миграция. Файл с записанной миграцией представляет собой
автоматически сгенерированный уникальный код для миграции. Файл с миграцией содержит две функции, которые называются
upgrade() и downgrade(). Функция upgrade() применяет миграцию, а функция downgrade() удаляет ее. Это позволяет Alembic
переносить базу данных в любую точку истории, даже в более старые версии, используя путь понижения версии.
Команда flask db migrate не вносит никаких изменений в базу данных, она просто генерирует сценарий миграции. Чтобы применить
изменения к базе данных, необходимо использовать команду:
    flask db upgrade
Поскольку это приложение использует SQLite, команда upgrade обнаружит, что база данных не существует, и создаст ее
(вы заметите, что после завершения работы этой команды добавляется файл с именем app.db, который является базой данных SQLite).
При работе с серверами баз данных, такими как MySQL и PostgreSQL, необходимо создать базу данных на сервере баз данных
перед запуском upgrade. По умолчанию, создаваемым в БД таблицам присваиваются имена как прописаны в моделях. Если вы
предпочитаете выбирать собственные имена таблиц, вы можете добавить атрибут с именем tablename в класс модели, присвоив
ему желаемое имя в виде строки.

На данный момент приложение находится в зачаточном состоянии, но не помешает обсудить, какой будет стратегия миграции
базы данных в будущем. Представьте, что у вас есть приложение на компьютере разработчика, а также есть копия, развернутая
на рабочем сервере, который подключен к сети и используется. Допустим, что для следующего выпуска вашего приложения вам
необходимо внести изменения в ваши модели, например, необходимо добавить новую таблицу. Без миграций вам нужно было бы
выяснить, как изменить схему вашей базы данных, как на вашей машине разработки, так и затем снова на вашем сервере, и
это могло бы потребовать много работы. Но благодаря поддержке миграции баз данных после изменения моделей в вашем
приложении вы создаете новый сценарий миграции (flask db migrate), просматриваете его, чтобы убедиться, что автоматическая
генерация выполнила все правильно, а затем применяете изменения к своей базе данных разработки (flask db upgrade). Вы
добавите сценарий миграции в систему управления версиями и зафиксируете его. Когда вы будете готовы выпустить новую
версию приложения на свой рабочий сервер, все, что вам нужно сделать, это получить обновленную версию вашего приложения,
которая будет включать новый сценарий миграции, и запустить flask db upgrade. Alembic обнаружит, что производственная
база данных не обновлена до последней версии схемы, и запустит все новые сценарии миграции, которые были созданы после
предыдущего выпуска.
Как я упоминал ранее, у вас также есть flask db downgrade команда, которая отменяет последнюю миграцию. Хотя вам вряд ли
понадобится эта опция в производственной системе, она может оказаться очень полезной во время разработки. Возможно, вы
сгенерировали сценарий миграции и применили его только для того, чтобы обнаружить, что внесенные вами изменения не совсем
то, что вам нужно. В этом случае вы можете понизить рейтинг базы данных, удалить сценарий миграции, а затем сгенерировать
новый для его замены.
    Для удаления таблиц в БД или возвращения БД в предыдущее состояние нужно ввести следующие команды в терминале:
    flask db downgrade base  # если не задан целевой параметр, понижает состояние на одну ревизию. Значение base понижает
                                до состояние БД до исходного, т.е. без таблиц
    flask db upgrade  # обновляет состояние БД

Документация Gravatar: https://gravatar.com/site/implement/images
Для добавления аватар, в этой главе, используется сервис Gravatar. Для получения аватара для текущего пользователя
необходимо использовать URL в формате https://www.gravatar.com/avatar /<хэш>, где <hash> - хэш MD5 адреса электронной
почты пользователя.
Пример получения аватара для пользователя susan по её почте:
    >>> from hashlib import md5
    >>> 'https://www.gravatar.com/avatar/' + md5(b'susan@example.com').hexdigest()
возвратится: 'https://www.gravatar.com/avatar/f3fc30174d7fd74ab6ca3c36d198fcb9' - хэш аватара. По умолчанию возвращаемый
размер изображения составляет 80x80 пикселей, но можно запросить другой размер, добавив аргумент s в строку запроса URL.
Например, чтобы получить свой собственный аватар в виде изображения размером 128х128 пикселей, используйте
URL https://www.gravatar.com/avatar/729e26a2a2c7ff24a71958d4aa4e5f35?s=128.
Еще один интересный аргумент, который может быть передан Gravatar в качестве аргумента строки запроса, - это d, который
определяет, какое изображение Gravatar предоставляет пользователям, у которых нет аватара, зарегистрированного в сервисе.
Один из таких называется "identicon", который возвращает красивый геометрический дизайн, который отличается для каждого
электронной почты.
Некоторые расширения веб-браузера для обеспечения конфиденциальности, такие как Ghostery, блокируют изображения Gravatar,
поскольку считают, что Automattic (владельцы сервиса Gravatar) могут определять, какие сайты вы посещаете, на основе
запросов, которые они получают к вашему аватару. Если вы не видите аватары в своем браузере, подумайте, что проблема
может быть связана с расширением, которое вы установили в своем браузере. Поскольку аватары связаны с пользователями,
имеет смысл добавить логику, которая генерирует URL-адреса аватаров, в модель пользователя.

Для того, чтобы проверить работу приложения с учетом дополнений выполняемых в этой главе, нужно вызвать ошибку в работе

Далее 3 варианта проверки отправки эл. писем:
    1. По туториалу
        Все данные берутся из переменных окружения (Environment Variables), чтобы не «светить» пароли прямо в коде.
        Использование os.environ.get — это золотой стандарт безопасности. Если вы выложите код на GitHub, никто не узнает
        ваш пароль от почты, так как он хранится только на вашем компьютере в настройках системы или в файле .env
        MAIL_SERVER = os.environ.get('MAIL_SERVER')  # адрес почтового сервера (например, ://google.com или smtp.yandex.ru)
    MAIL_PORT = int(os.environ.get('MAIL_PORT') or 25)  # порт сервера. Код int(... or 25) пытается взять порт из настроек,
                                                        # а если его там нет — использует стандартный 25
    MAIL_USE_TLS = os.environ.get('MAIL_USE_TLS') is not None  # флаг безопасности. Если в переменных окружения задано это
                                                        # свойство, будет использоваться шифрование TLS (безопасное соединение).
    MAIL_USERNAME = os.environ.get('MAIL_USERNAME')  # имя пользователя/логин от почты с которого приложение будет
                                                    # отправлять письма
    MAIL_PASSWORD = os.environ.get('MAIL_PASSWORD')  # пароль от почты, с которого приложение будет рассылать письма
    ADMINS = ['your-email@example.com']  # список email-адресов администраторов, на которые приложение будет рассылать

        pip install aiosmtpd
        далее запуск отладочного почтового сервера:
        aiosmtpd -n -c aiosmtpd.handlers.Debugging -l localhost:8025

        раз, чтобы увидеть, как сеанс терминала, на котором запущен поддельный почтовый сервер, показывает электронное
        письмо с полной трассировкой стека ошибки.

Добавление и удаление "подписчиков". Предположем есть два пользователя: user1 и user2. Для подписки и отписки этих
пользователей можно было бы использовать следующие две команды:
    user1.following.add(user2) - делает user1 подписчиком user2
    user1.following.remove(user2) - отписывает пользователя user1 от пользователя user2
Но вместо этого, лучше использовать функциональный подход и отдельно создать соответствующие фнукции/методы - "подписаться",
"отписаться" в качестве методов в модели User.

Чтобы проверить работу приложения на этом этапе, можно запустить приложение, создать нескольких пользователей и поиграть
с подписчиками и отписавшимися пользователями. Единственное, что вам нужно запомнить, это ввести URL страницы профиля
пользователя, на которого вы хотите подписаться или отписаться, поскольку в настоящее время нет возможности просмотреть
список пользователей. Например, если вы хотите подписаться на пользователя с именем пользователя susan , вам нужно будет
ввести http://localhost:5000/user/susan в адресной строке браузера, чтобы получить доступ к странице профиля этого
пользователя. Убедитесь, что вы проверили, как меняется количество подписанных пользователей по мере того, как вы
подписываетесь или отменяете подписку

CH13
В этой главе демонстрируется поддержка в приложении нескольких языков с использованием расширения Flask-Babel. Он авто-
матически определяет язык пользователя на основе настроек его браузера (через заголовки headers).
установка:
    pip install flask-babel
Конкретно в этом приложении будет показан пример поддержки английского и испанского языков.
Все тексты во всех файлах требующие перевода, я буду оборачивать в функции _() и lazy_gettext() (импортированный как _l())
Процесс перевода состоит из трех шагов:

1. Извлечение текстов для переводов.
Все тексты в разных файлах (.py, .html) переданные в функции _() и _l() для переводов, необходимо собрать в одном .pot-файле.
Для этого используется команда в терминале - pybabel extract. Для того, чтобы pybabel знал в каких файлах искать тексты
для извлечения, необходимо создать конфигурационный файл с расширением .cfg в котором и будут прописаны эти файлы. Например,
для этого приложения я создам файл babel.cfg. После того как .cfg-файл создан, можно собрать все тексты в один .pot-файл.
В случае данного приложения это можно сделать командой в терминале:
    pybabel extract -F babel.cfg -k _l -o messages.pot .
    расшифровка этой крманды:
    pybabel extract считывает файл конфигурации, указанный в опции -F , затем сканирует весь код и файлы шаблонов в каталогах,
    соответствующих настроенным источникам, начиная с каталога, указанного в команде (текущий каталог или . в данном случае).
    По умолчанию, pybabel будет искать _() в качестве текстового маркера, но поскольку я также использовал отложенную
    версию, которую я импортировал как _l(), мне нужно сказать инструменту, чтобы он искал их с помощью -k _l. Параметр -o
    указывает имя выходного (создаваемого) .pot-файла, в данном случае это будет messages.pot (созданный файл будет с
    расширением .po, а не .pot).

ВАЖНЫЙ момент.
    !!! Файл с расширением .pot (Portable Object Template) — это шаблон. Он содержит только исходные строки из кода, т.е. до
    перевода (msgid), а строки перевода (msgstr) в нем всегда пустые. Он создается один на весь проект.
    Файл с расширением .po (Portable Object) — это готовый файл уже с переводом для конкретного языка (например, ru.po,
    fr.po). В него копируются строки из шаблона (.pot), и переводчик заполняет поля msgstr. Если случайно сгенерировать
    шаблон с расширением .po вместо .pot, то .po все равно будет шаблоном и содержать исходный текст (msgid) без перевода.
    Расширение можно изменить в ручную !!!

2. Создание языкового каталога и перевод
Следующим шагом в процессе является создание перевода для каждого языка, который будет поддерживаться в дополнение к
базовому, которым в данном случае является английский. Я собираюсь начать с добавления испанского (код языка es), так что
вот команда, которая делает это:
    pybabel init -i messages.pot -d app/translations -l es creating catalog app/translations/es/LC_MESSAGES/messages.po
    based on messages.pot
    расшифровка этой команды:
    Команда pybabel init принимает файл messages.pot в качестве входных данных и записывает новый языковой каталог в каталог,
    указанный в опции -d для языка, указанного в опции -l . Я собираюсь установить все переводы в каталог app/translate,
    потому что по умолчанию Flask-Babel ожидает, что именно там будут находиться файлы переводов. Команда создаст подка-
    талог es внутри этого каталога для файлов данных на испанском языке. В частности, появится новый файл с именем
    app/translations/es/LC_MESSAGES/messages.po, именно там необходимо выполнить переводы.
    Для добавления других языков, нужно просто повторить приведенную выше команду для каждого языка
Для перевода подготовленных текстов для перевода в каталогах используются соответствующие приложения, например - poedit (https://poedit.com/),
можно также использовать плагин po.vim (https://sourceforge.net/projects/vim/)

3. Компиляция переводов
Чтобы изменения вступили в силу в работе приложения, необходимо скомпилировать .po-файл в бинарный .mo командой в консоли:
    pybabel compile -d app/translations compiling catalog app/translations/es/LC_MESSAGES/messages.po to app/translations/es/LC_MESSAGES/messages.mo
    Эта команда добавляет файл messages.mo рядом с messages.po в репозитории каждого языка. Файл .mo - это файл, который
    Flask-Babel будет использовать для загрузки переводов в приложение. После создания файла messages.mo для испанского
    или любых других языков, добавленных вами в проект, эти языки готовы к использованию в приложении. Компилировать можно
    и не полностью переведенные кталоги, не переведенная часть каталога будет отображаться в приложении на базовом языке.
    Это значит, что компиляцию можно делать не один раз, по мере добавления переводов. Для последующих компиляций нужно
    выполнить следующие команды:
    pybabel extract -F babel.cfg -k _l -o messages.pot .
    pybabel update -i messages.pot -d app/translations
    Команда extract идентична той, которую была выполнена ранее, но теперь она сгенерирует новую версию messages.pot со
    всеми предыдущими текстами плюс все новое, что было добавлено в _() или _l(). Вызов update принимает новый файл
    messages.pot и объединяет его со всеми файлами messages.po , связанными с проектом. Это будет интеллектуальное
    объединение, при котором все существующие тексты будут оставлены в покое, а записи, которые были добавлены или удалены
    в messages.pot будут затронуты.

Переводы даты и времени.
После перевода текстов, в приложении остались непереведенными временные метки, которые были сгенерированны Flask-Moment

к нему доступ из базового шаблона.

CH14
В этой главе показан Ajax-метод обновления страницы в приложении. Этот метод используется так называемыми - однострани-
чными приложениями. Суть этого метода заключается в том, что клиент с первым запросом на сервер получает html-шаблон
страницы плюс дополнительный скрипт для работы страницы, скрипт обычно написанный на JavaScript, этот дополнительный
скрипт часто запускается не сразу, а просто настраивает обработчики событий для запуска в браузере в ответ на действия,
инициированные пользователем. Этот скрипт работает автономно, практический не контактируя с сервером, контакт с сервером
происходит только для извлечения или сохранения данных и внося динамические изменения в внешний вид первоначально полу-
ченной веб-страницы.
В данном приложении Ajax-метод будет использован для автоматического перевода сообщений написанных на разных языках.
Для реализации автоматического перевода в реальном времени требуется несколько шагов. Во-первых, нужен способ определить
исходный язык текста для перевода. Нужно знать предпочтительный язык для каждого пользователя, чтобы показывать ссылку
"перевести" только для сообщений, написанных на других языках. Когда будет предложена ссылка на перевод и пользователь
нажмет на нее, нужно будет отправить Ajax-запрос на сервер, и сервер свяжется со сторонним API перевода. Как только сер-
вер отправит ответ с переведенным текстом, клиентский JavaScript-код динамически вставит этот текст на страницу.

Ajax (асинхронный перевод) на стороне сервера.
    Когда пользователь нажимает на ссылку "Перевести", которая появляется под сообщением, на сервер отправляется асинхронный
    HTTP-запрос. Асинхронный (или Ajax) запрос аналогичен функциям маршрутов и просмотра, которые я создал в приложении,
    с той лишь разницей, что вместо возврата HTML или перенаправления он просто возвращает данные, отформатированные как
    XML или, чаще, как JSON. В модуль routes.py я добавлю функцию просмотра/обработчик перевода текста

Ajax на стороне клиента
    Теперь, когда сервер может предоставлять переводы по маршруту/URL-адресу /translate, нужно вызывать этот URL-адрес,
    когда пользователь нажимает ссылку "Перевести", передавая текст для перевода, а также языки источника и назначения.
    При работе с JavaScript в браузере отображаемая в данный момент страница внутренне представлена в объектной модели
    документа или DOM. Другими словами, DOM — это то, как браузер видит ваш сайт изнутри. Для него страница — это не просто
    текст, а дерево из элементов (заголовки, абзацы, кнопки, картинки). JavaScript умеет «ходить» по этому дереву, находить
    нужные элементы, читать из них текст или заменять его на другой. То есть, код JavaScript, выполняемый в этом контексте,
    может вносить изменения в DOM, чтобы вызвать изменения на странице. Задача заключается в следующем:
    1 - Найти на странице иностранный текст, который нужно перевести.
    2 - Узнать, с какого языка и на какой мы переводим.
    3 - Незаметно отправить эти три вещи на сервер по адресу /translate.
    Чтобы выполнить 1 пункт, нужно каждому интересующему элементу DOM (в данном случае текст поста для перевода), назначить
    уникальный идентификатор (ID) в шаблоне. Идентификаторы можно добавлять с помощью тега <span>. В случае с постами,
    идентификация поста выглядит так:
        <span id="post{{ post.id }}">{{ post.body }}</span>
    Исходный язык записан в БД, согласно моей модели Post (post.language), а
    целевой язык хранится в объекте g.local (получается из хидера запроса клиента). Когда есть решения для первых двух
    пунктов, можно использовать функцию document.getElementById(), чтобы найти элемент DOM-элемент для этого поста и извлечь
    из него текст. Например, если нужно получить текст для записи с идентификатором 123, то можно сделать это:
        document.getElementById('post123').innerText  # эта команда выполняет поиск DOM-элемента по коду страницы.
    Помимо изложенного, необходимо иметь в шаблоне место, куда будет вставляться переведенный текст, когда он будет получен
    с сервера. Для этого можно заменить ссылку "Перевести" переведенным текстом, и назначить этому месту также идентификатор:
        <span id="translation{{ post.id }}"><a href="#">{{ _('Translate') }}</a></span>
    Следующий шаг - написать функцию, которая может выполнять всю работу по переводу. Эта функция будет использовать входные
    (исходный текст поста) и выходные (переведенный текст поста) узлы DOM, а также языки источника и назначения. Затем она
    отправит асинхронный запрос серверу с тремя необходимыми аргументами и, наконец, заменит ссылку на перевод переведенным
    текстом, возвращаемым сервером. Для удобства эта функция будет добавлена в базовый шаблон (base.html) внизу элемента
    <body>, чтобы она была доступна на всех страницах приложения.
